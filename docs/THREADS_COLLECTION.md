# Накопление истории Threads

Следующий этап улучшения модели требует новых наблюдений, а не повторной настройки прежних столбцов. Доступа к Meta API пока нет; сбор реальных профилей и их полных историй ещё не выполнялся.

## Что сохранять при каждом наблюдении

Использовать canonical Dataset JSON: accounts, posts, observation. Для аккаунта нужны platform, стабильный external_user_id, collected_at в UTC, известные followers/following/biography/has_avatar. Неизвестные значения оставлять null. Username не считать стабильным ID. Поля профиля должны описывать момент collected_at, а не дату старого поста.

Посты: стабильные external_post_id и author_id, created_at в UTC, text и известные urls/targets. targets — стабильные идентификаторы адресатов, полученные из источника; не угадывать их по тексту. null означает неизвестно; [] — достоверно пустой список. Одна публикация может содержать несколько URL. Сохранять оригинальные импорты: они нужны для истории изменения профилей и проверки происхождения.

Observation.start/end — реальный период, который покрывал запрос. complete=true допустимо только при подтверждённой полноте аккаунтной истории за весь период и завершённой пагинации. Завершение keyword search само по себе не подтверждает полноту аккаунтной истории. Ограничение выдачи, ошибки и пропущенные страницы фиксировать; не подменять их отсутствием активности.

Для первого пилота предлагается регулярно сохранять наблюдения в течение14дней. Это план сбора, не доказанный минимальный объём для качественной модели. Частота запросов зависит от доступного источника и его лимитов. Требуется достаточное представительство небольших человеческих аккаунтов и ботов с заполненными профилями; независимый контроль должен сохранять целевую распространённость классов, а не состоять только из очевидных случаев.

## Объединение файлов

```sh
.venv/bin/python -m scripts.merge_observations /path/day1.json /path/day2.json --output media/history/batch-001
```

Получатся dataset.json для существующего импорта Django и coverage.json с SHA256 входов, исходными окнами, числом дублей, количеством наблюдённых постов, известностью targets и явных URLs. Выходная папка должна быть новой. Размер объединённого Dataset ограничен10000аккаунтов/100000постов; большие наборы разбивать заранее, не усекать незаметно.

Совпадающие посты удаляются как дубли. Конфликтующее содержимое одного ID вызывает ошибку: отредактированный пост или обогащение метаданных требуют явного согласования. Для различных профилей выбирается снимок с самым поздним collected_at; конфликт без дат или с одинаковыми датами останавливает объединение. Старые профили остаются в исходных файлах. Итоговый JSON — текущий снимок, его нельзя использовать как исторические признаки для каждого старого поста.

Результат всегда complete=false. Склейка неполных или разнесённых окон не доказывает полноту промежутков. Временные признаки обучения остаются выключены до отдельной проверки покрытия. Поля targets/urls лишь сохраняются; сама их доступность не доказывает координацию или ботоводство.

## Дальнейшие эксперименты

После накопления наблюдений: аудит пропусков/окон и стабильности ID; затем интервалы и повторяемость активности на подтверждённых полных окнах, повторные общие ссылки/адресаты на наблюдаемой истории. Сначала независимая ручная разметка, затем разбиение по аккаунтам/группам и времени. Сравнение при одинаковой ёмкости очереди; контрольный набор не использовать для настройки.

Сейчас сделана инфраструктура накопления, не сбор новых реальных данных. Действующая профильная модель и локальный стенд не изменены. Демонстрационный прогон объединения двух одинаковых примеров дал2поста вместо4 и сохранил incomplete.
