## 1. Что строим

Систему анализа аккаунтов социальной сети **Threads** на признаки автоматизации и координации.

- **Django** — пользовательский интерфейс, авторизация, CRM, админка и ручная разметка.
- **FastAPI** — внутренний API импорта, сбора, подготовки признаков и распознавания.
- **Celery + Redis** — фоновые задания.
- **ML-ядро на Python** — общие преобразования для обучения и распознавания, без Django ORM.
- **TwiBot-22 / Twitter** — исходный размеченный набор для обучения.
- **Threads** — целевая платформа, на которой качество нужно отдельно проверить.

Признаки первой версии не требуют словарей языка, TF-IDF или языковых эмбеддингов. Это не делает их автоматически независимыми от письменности, региона или платформы. Перенос Twitter → Threads должен подтверждаться данными.

Результат — исследовательская оценка с объяснением и покрытием данных, а не доказательство того, что владелец аккаунта является ботом. Координация и автоматизация оцениваются отдельно.

## 2. Что считать рабочим MVP

### MVP-1: работа через импорт файлов

Пользователь входит в Django, загружает реальные данные Threads в CSV/JSONL/JSON, получает фоновое задание, затем оценку установленной модели или понятный отказ при недостатке данных. В CRM можно изучить причины оценки, поставить ручную метку и сохранить заметки. Данные разных пользователей изолированы.

Для этого **не обязателен доступ к Meta API**, но обязательны совместимые входные данные, обученный артефакт и проверка всей цепочки с настоящей моделью. Прогон только примера без модели доказывает работу импорта, но не готовность детектора.

### MVP-2: живой сбор Threads

Всё из MVP-1 плюс реальный сбор по поддерживаемому сценарию через проверенный API-адаптер. Пользователь вводит запрос; система собирает доступные публикации, показывает ограничения выборки и отправляет данные в модель.

Важно: текущий адаптер ищет **публикации по ключевым словам**. Он не реализует универсальную проверку произвольного профиля по ссылке и не гарантирует получение его полной истории. Проверка по username/URL — отдельное расширение после аудита доступных API-возможностей.

**Рекомендуемый порядок:** довести MVP-1, затем подключать MVP-2. Профильный Twitter baseline можно использовать как промежуточный эксперимент, но нельзя выдавать его за проверенный детектор Threads.

## 5. Главный риск: модель и сборщик могут видеть разные признаки

Исходный профильный набор Twitter содержит followers/following и описание профиля. Текущий Threads collector запрашивает в основном текст, время и тип публикации. Он **не заполняет** followers/following, biography и аватар аккаунта.

Поэтому нельзя просто обучить профильную модель, положить её в `portable.joblib` и считать интеграцию законченной: на данных текущего collector она может закономерно возвращать `insufficient_data`.

Выполнен аудит миллиона профилей против синтетического примера — пересечение
с покрытием ≥50% отсутствует. На sample из реальных tweets пересекаются девять
признаков структуры текста/URL. Это не аудит реального API и не проверка качества.

Перед выбором первой рабочей модели составить таблицу **фактически доступных** полей:

| Группа | TwiBot-22 сейчас | Текущий collector Threads | Решение |
|---|---|---|---|
| Followers/following, bio, avatar | Частично есть | Не собирает | Дополнить источник или не опираться на них в целевой модели |
| Структура/дубликаты текста | Есть в частичном tweet-sample | Может получить | Нужны tweets и сопоставимая выборка |
| Reply/quote/media | Частично; media extraction ещё ограничен | Зависит от ответа | Проверить семантику; отсутствующее поле не превращать в false |
| Интервалы и интенсивность | Нет подтверждённого полного окна | Keyword search — неполная история | В текущем контракте останутся null |
| Подписки и follower-граф | Нет в открытой части | Не реализованы | Не включать как обязательную зависимость MVP |

Существующий `extract_features` намеренно подавляет временные признаки при неполном наблюдении. Не менять это правило ради получения числа. Если понадобится модель по неполным выборкам, явно определить новый набор выборочных признаков, воспроизвести процедуру выборки на Twitter, изменить версию схемы и проверить её отдельно.

### Этап D — обучить и оценить первый baseline [P0; только после отдельного разрешения]

1. Перед запуском проверить CPU/RAM/диск. Текущий `train_model` читает train/val через `to_pylist()` целиком: чтение только выбранных столбцов и уменьшение Python-объектов может потребоваться до большого fit.
2. Повторно проверить prepared-набор и экспериментальный конфиг.
3. Начать с простого контрольного baseline и XGBoost; сравнить с тривиальным предсказанием класса/априорной доли.
4. Все обучаемые преобразования подбирать на train; гиперпараметры и порог — на val.
5. Не использовать test для повторного выбора признаков и порога. Финальную оценку проводить после фиксации решения.
6. Сохранить precision/recall/F1 класса bot, macro-F1, PR-AUC, ROC-AUC, confusion matrix и калибровочные характеристики.
7. Проверить долю отказов `insufficient_data`, а не только метрики на оставшихся объектах.
8. Проверить поведение при недостижимом `min_precision`: существующий флаг не должен превращаться в обещание качества в UI.
9. Сохранить доверенный артефакт с feature/model version, порогом, seed, версиями зависимостей, источником данных и отчётом. Сейчас список зависимостей в metadata неполный: добавить как минимум версию XGBoost и воспроизводимое описание окружения.

**Готово, когда:** реальный артефакт обучен, отдельно оценён, загружается `ModelService`, выдаёт числовой score и объяснение вклада признаков. Выбор параметров и ограничения воспроизводимы.

Профильный baseline на уже скачанных данных возможен как отдельная проверка ML-пути. Он не закрывает этап B и не заменяет поведенческую модель, если необходимые профильные поля недоступны в Threads.

**Готово, когда:** аналитик без терминала импортирует реальный файл, получает результат настоящей модели или обоснованный отказ, сохраняет разметку и возвращается к данным после повторного входа.

### Этап G — подключить живой Threads API для MVP-2 [P0 для live-сценария]

1. Пользователь создаёт/подключает приложение Meta и получает необходимые права; токен хранится в окружении.
2. Перепроверить актуальную официальную документацию, endpoint, поля, права и ограничения. Fixture-тесты не доказывают действующий API-контракт.
3. Проверить реальные запросы, включая нулевой результат, одну страницу, несколько страниц и нехватку разрешений.
4. Если нужны профиль или история аккаунта, реализовать отдельное обогащение только после проверки доступности соответствующих возможностей.
5. Сопоставить реальные ответы с `Dataset`, сохранять происхождение и неполноту выборки.
6. Проверить курсоры, дедупликацию, лимиты, истёкший токен и безопасное продолжение.
7. Не соединять `username:…` с платформенным ID по догадке. Username может изменяться.

**Готово, когда:** запрос из Django приводит к реальному сбору, затем к валидному входу модели. Число оценённых аккаунтов и отказов видно; ограничения данных явно обозначены.

### Этап H — минимальная эксплуатационная готовность [P0 перед внешним доступом]

1. Настроить production-сервер Django вместо `runserver`, static, HTTPS и reverse proxy.
2. Держать FastAPI внутренним: общий ключ сейчас доверяет Django задавать tenant. Публичный доступ к этому ключу разрушит изоляцию.
3. Закрыть или убрать из рабочего интерфейса старые общие demo-маршруты `/accounts/`, `/graph/`, `/data/` и их изменяющие операции; проверить авторизацию всех опубликованных маршрутов.
4. Ввести HTTP-лимит тела на proxy, контроль файлов/размеров и понятный таймаут ожидания.
5. Настроить резервное копирование обеих БД и модели, проверить восстановление.
6. Добавить наблюдение за очередью/failed jobs и регламент `--recover`. Не обещать мгновенный автоматический retry там, где он не реализован.
7. Проверить работу без модели: readiness сейчас 503, но импорт работает. Политика проверки готовности не должна закрывать весь импортный сервис из-за отсутствия ML.
8. Определить обновление/откат модели и схему изменений engine-БД: `metadata.create_all()` не заменяет миграции существующих таблиц.

**Готово, когда:** внешний пользователь видит только свои данные, секреты не попадают в браузер/логи, результаты и разметка восстанавливаются после сбоя. Для локального пилота внешнее развёртывание можно отложить, явно ограничив доступ localhost.

## 7. Зависимости и следующий конкретный шаг

```text
A: реальный запуск без модели ───────────────────────────────┐
B: аудит Threads-полей → C: нужные данные → D: обучение ─────┼→ F: MVP-1
                                      E: Threads-проверка ───┘
Права Meta → G: живой сбор + совместимость с моделью ──────────→ MVP-2
H: эксплуатационные проверки ─────────────────────────────────→ внешний доступ
```

**Ближайшая работа разработчика:** проверить отчёты завершённого этапа A,
затем определить репрезентативную выборку из скачанного фрагмента и реальный вход
Threads. Полный benchmark требует доступа авторов. Не повторять загрузку 12 ГБ
или создание окружения без проверки уже существующих файлов и контейнеров.

**Следующее решение о модели:** после этапа B выбрать набор, который реально наблюдается в обеих платформах. До этого большой fit на миллионе профилей может оказаться бесполезным для Threads.

## 9. Что не ломать при продолжении

- Не переносить ML и сбор обратно в Django views.
- Не вызывать fit из анализа, API, worker или обычного прогона тестов.
- Не ставить `RUN_LEGACY_TRAINING_TESTS=1` без намерения запускать старые обучающие тесты.
- Не подменять null нулём, отсутствующий флаг — false, а отсутствие модели — эвристическим score.
- Не использовать label, split, ID, будущие события и данные test для обучения/подбора.
- Не считать поиск по словам полной историей аккаунта.
- Не использовать текущее время как дату исторического Twitter-снимка.
- Не смешивать score бота и координацию в якобы калиброванную вероятность.
- Сохранять tenant-фильтры, идемпотентность, lease token и защиту CRM от старых результатов.
- Не загружать пользовательский joblib: десериализуются только доверенные артефакты оператора.
- Не удалять raw/processed, volumes или чужие незакоммиченные изменения ради «чистого запуска».

В предыдущем независимом ревью исправлены: ошибка одностраничной пагинации, потеря ссылки на SQL-job при сбое брокера, откат CRM старым анализом, смешение username с platform ID и сохранение результата устаревшим worker. Для них есть регрессионные тесты — сохранить эти гарантии.
